# 微信小游戏移植工程 · 《萌兽不好惹》

> 目标：把**单文件 HTML5 母版**变成**能上传微信小游戏平台**的代码包，为「小游戏备案 → 上架」铺路。
> 本目录不含母版副本；游戏逻辑的唯一真源仍是 `../mengshou-survivor/game/萌兽消消岛.html`。

⇒ 本工程是**单主包**（3.74MB），**不需要分包、不需要 CDN、不需要网络域名**。

  若将来要做回归基线，应先在沙箱里注入**定种子 PRNG** 替换 `Math.random`。

## 三·二、布局占用探针（`--layout`）—— 本项目长期缺的那只眼睛

```
node smoke.mjs --no-play --frames 60 --layout   # 量**首页**布局
node smoke.mjs --play-frames 300 --layout       # 量**局内**布局
```

做法：给画布上下文套 **Proxy**，记录**上屏画布**上每次绘制的**包围盒**，并自行维护
`setTransform / transform / translate / scale / rotate / save / restore` 的**变换矩阵**
（实测 `setTransform` 占全部绘制调用的 **31%** —— 纯静态坐标扫描根本看不到变换后的坐标系）。
路径类用 `moveTo/lineTo/arc/rect/roundRect` 累积包络，在 `fill/stroke` 时落账。

产出：竖直 32 段剖面（段均值）+ 热图 PNG + 底部带按类型/按 y 的细查。

> ⚠ **关键口径**：**"全部绘制"的覆盖率必然 100%**（背景/暗角/边框铺满全屏），这个数**没有信息量**。
> 必须剔除"包围盒面积 ≥ 屏幕 5%"的背景大块，只看**内容元素**，才回答得了"哪里空"。
> 首页实测：全部 100.0% vs 内容 **65.4%**。这个坑和项目第 10 轮那次同源。

**首次用它验到的两件事**（首页，60 帧）：
1. **《健康游戏忠告》确实被渲染**：底部带 `fillText` 出现在 device y 2480–2500 与 2500–2520，各 **60 次**
   （= 每帧一次），正好对应逻辑 y1252 / y1270 那两行 —— 此前这个改动只有静态坐标推断，**没有运行时证据**。
2. 首页有一条**完全空白带**：device y **1760–1920**（逻辑 y 880–960）内容元素 **0 个**，
   热图 `_dsh-kit/aa-test/layout-home.png` 里肉眼可见。

两个阴性对照都验过：抽掉 `document` → ② 立刻 `document is not defined`；
拿内联母版构建 → 判据报"残留内嵌美术 178 处"。

## 三·三、深度实战：喂走位打到 BOSS（`--move`）

不带输入时玩家**站桩，约 10 秒阵亡**，后期系统（BOSS/怪潮/章节结算）**根本跑不到**。
`--move` 让测试直接写游戏自己的输入状态 `Input.joy`（不必猜触摸坐标）。躲避策略是**量出来的**，
不是假设的 —— 同一 36000 帧（≈10 分钟时间戳）下五版对比：

| 策略 | `runTime` | 重开 | 结局 |
|---|---|---|---|
| 不喂输入 | 10.5 s | 0 | 站桩阵亡 |
| 盲目转圈 | 16.3 s | 3 | 仍反复阵亡 |
| **躲最近敌人** | **180.0 s** | 1 | **打到 BOSS** |
| 多点 1/d² 排斥 | 69.4 s | 2 | **更差**（玩家被逼到顶边 y=119）⇒ 我的"改进"被实测推翻 |
| **躲最近敌人 + 自校准防贴边** | **180.0 s** | 2 | **打到 BOSS，且玩家在场地中央 (694,683)** |

**BOSS 的判定证据**（不是猜的 —— 源码注释「主时钟…BOSS 战计时暂停」）：

```
runTime=180.0  game.time=192.7  bossWarnIdx=0  bossState.active=true
```

`runTime` **冻结在第 1 章的 boss 时刻 180 秒**、`game.time` 继续走到 192.7 秒（＝已交战 12.7 秒）、
`bossState.active=true` ⇒ 测试**进到了 BOSS 战**。

**性能（设备无关的那部分）**：绘制调用/帧 **中位 560、最小 164、最大 3741**（中位随游戏进程变密：
短局 459 → 长局 560）。⚠ 这个数比 Node 的 ms/帧 更有参考价值（微信画布每次调用都有开销），
但仍**不等于真机帧率**。

```
node smoke.mjs --move --play-frames 36000   # ≈10 分钟游戏时间，打到 BOSS
```

## 三·四、输入坐标映射（对照 `--bad-rect`）—— 一个「点不动」级别的移植缺陷

母版 `pointerToView`（L13276）用**画布的显示盒**把 client 坐标归一到 720×1280：

```js
var rect = CANVAS.el.getBoundingClientRect();
x = (e.clientX - rect.left) * CONFIG.viewW / rect.width;
```

而母版自己会按窗口算出 letterbox 尺寸并写 `CANVAS.el.style.width = cssW + "px"`
（实测 **375 × 666.67**），内部缓冲则是 **1440 × 2560**。
适配层最初把 `getBoundingClientRect()` 写成返回**内部尺寸** ⇒ 换算变成 ×0.5：

| | 屏幕中心 (187.5, 333.5) 映射到 |
|---|---|
| 修复前（返回内部 1440） | view(**93.8, 166.8**) ❌ 只到四分之一处 |
| 修复后（按 `style` 的显示盒） | view(**360, 640.3**) ✅ 正是逻辑中心 |

后果本会是：**每次点击都偏到左上、屏幕大半区域点不动** —— 而前 11 个阶段照样全绿
（阶段 ⑤ 只验「事件派发了」，**没验「点到的地方对不对」**）。

修法：适配层的显示盒**由 `style.width/height` 决定**（没设时回落到窗口尺寸），
并**无条件覆盖**宿主自带的同名实现（本机桩返回的正是内部尺寸，照抄就会踩坑）。
专项阶段 **⑫** + 阴性对照 `--bad-rect`（把显示盒伪装成内部尺寸 → ⑫ 报
「屏幕中心映射到 view(93.8,166.8)，期望约 (360,640) —— 点击会偏位」）。


## 三·五、设备剖面与安全区（`--device` / `--safe`）—— 又抓到一个"静默失效"

用法：

```
node smoke.mjs --no-play --frames 60 --layout --device 390x844 --safe 47   # 刘海机
node smoke.mjs --no-play --frames 60 --layout --device 375x667             # 基线
```

**① 出屏体检：4 种剖面全部通过。**
越过画布边界的内容元素 **0 个**（375×667 / 390×844+刘海47 / 412×915+刘海24 / 360×640），
内容横向用到 **1440 / 1440**（铺满）。这一条对应的正是云端 `ci/ui-fit.mjs`
（「控件出屏」是审核真会卡的点，而它**需要 playwright，本机跑不了**）。

> ⚠ 这个判据**第一版报的是假阳性**：它把 `fillText` 的 x 一律当左边缘，
> 于是居中文案（`textAlign:'center'`，x=720 正是水平中心）被算成 `box(720..1952)` ——
> 画布才 1440 宽，于是报「347 个元素出屏」。**差一点把正常布局报成"控件出屏"**。
> 修法是尊重 `textAlign` 后再算包围盒 → 假阳性全部消失（0 个）。

**② 安全区 / 纵横比：✅ 已修（第 34 轮）—— 把 letterbox 从 CSS 搬进绘制路径**

原缺口（第 32 轮定位、第 33 轮试修的 inset 方案**已实测否决**）：母版把 9:16 内容画进**固定 1440×2560 后备缓冲**，
浏览器里靠 CSS 把 canvas 摆成 letterbox 盒（390×693 居中，上边距 **75px > 刘海 47px**）；
小游戏**没有 CSS 排版**，显示画布恒铺满屏幕 ⇒ 三个后果：

1. 后备缓冲被拉伸铺满 ⇒ 19.5:9 上**纵向拉伸 ≈21.7%**（`844 ÷ (390×2560/1440) = 1.217`）
2. 内容顶边落在屏幕 y=0 ⇒ **刘海压住首页顶栏/标题**（实测带内文字 **30** 个）
3. `getBoundingClientRect` 报的显示盒与实际不符 ⇒ 点击纵向偏移

**修法（`adapter.js`，不改游戏源码）**：

1. 后备缓冲**钉在屏幕物理尺寸**上 —— 游戏写 `width/height` 会被纠回，**但先把它写的值当作设计尺寸记下来**
   （⚠ 不能写死 1440×2560：低端机上母版把 `CONFIG.dprCap` 降到 1，设计缓冲是 720×1280，写死会让画面缩到左上角）；
2. 把游戏每次 `setTransform(dpr,0,0,dpr,tx,ty)` 与 letterbox 矩阵 `L=(s,0,0,s,ox,oy)` **复合**（`L·M` 仍是 scale+translate）；
   `resetTransform()` 也必须设成 L（原生 reset 会丢掉 letterbox）；
3. `getBoundingClientRect()` 改报**居中内容盒**（CSS px）⇒ 输入映射自动对齐。

**实测（`--device 390x844 --safe 47`）**：

| 项 | 修前 | 修后 |
|---|---|---|
| 内部缓冲 | 1440×2560（被拉伸铺满，纵向 +21.7%） | **780×1688**（= 屏幕物理尺寸，**无拉伸**） |
| 显示盒（CSS） | 390×693.3（与实际不符） | **390×693.33** ✅ 9:16 |
| 落进刘海带的内容元素 | **120**（其中文字 **30**） | **0** ✅ |
| 母版 `viewSafe.top` | 86.77（会去 inset 满幅页头） | **0** ✅（刘海落在空带里，与浏览器同解） |
| 越出画布边界 | 0 | **0** |
| 坐标映射 ⑫ | 通过 | **通过**（屏幕中心 → 逻辑 360,640） |
| 整套 `smoke`（含 900 帧实战 + 存档 ⑬） | exit 0 | **exit 0** |

**几何自检**：`s = min(780/1440, 1688/2560) = 0.54167` ⇒ 内容 `780 × 1386.7`，宽高比 `0.5625` = **9:16 精确**；
上下空带各 `150.7` 缓冲px = **75.3 CSS px > 刘海 47** ✅。

⇒ **小游戏现在与浏览器同一个解**：letterbox 让位刘海、无纵横比失真、点击映射一致。

⚠ 仍未验：**真机 / 开发者工具的光栅化观感**（本机探针只验几何与映射，不做光栅化）。

### 安全区来源（v1.196）：修完 letterbox 之后才**真正生效**（第 35 轮）

"宿主真实 safeArea 优先"这一条**上线时是假生效的**：适配层里**游戏看到的 `window` 是自建的独立对象 `win`**，
而 `__wxadapter` 只挂在 `root` 上 ⇒ 母版 `window.__wxadapter` 永远 undefined（实测：宿主给 24/44 的剖面仍报启发式的 **47**）。
已在适配层补 `win.__wxadapter = root.__wxadapter`，修后回显正确：

| 宿主 safeArea.top | 母版 SafeArea.top | 母版 viewSafe.top |
|---|---|---|
| 44 | **44** ✅ | 0 |
| 24 | **24** ✅ | 0 |
| 47 | **47** ✅ | 0 |

`viewSafe.top` 仍为 0 ⇒ 刘海由 letterbox 让位，**布局零变化**。

### letterbox 的确定性收益（可逐项复算）

| 设备 | 修前后备缓冲 | 修后后备缓冲 | 主缓冲像素量 |
|---|---|---|---|
| 390×844 | 1440×2560 = **3.69 Mpx** | 780×1688 = **1.32 Mpx** | **−64%** |
| 设计→缓冲缩放 | ×2.0（超采样，随后被拉伸） | ×1.083（**原生 1:1**） | 单次绘制填充面积 **≈ −71%** |

⇒ 既无画质损失（缓冲 = 屏幕物理分辨率 = 显示上限），又省约 2/3 填充量。
⚠ 不跨轮次对比 `画布台账` 总 Mpx：其中含离屏烘焙画布，且**质量档位在不同轮次可能不同**（是噪声）。


## 三·六、存档往返（跨进程）—— 本地首次能跑这个口径

阶段 ⑥ 只验「发生过写入」，**验不到「读回来对不对」**——读不回来 = 玩家进度**静默丢失**。
云端 `ci/save-integrity.mjs` 同样需要 playwright（本机跑不了）。本轮补跨进程往返：

```
node smoke.mjs --move --play-frames 3000 --dump-save save-a.json   # A：打完一局落盘
node smoke.mjs --load-save save-a.json --frames 30                 # B：带着它冷启动
```

| 项 | 数值 |
|---|---|
| 持久化 wrapper | **`{ d, chk }`**（带校验和 ⇒ `validateSave` 会验签） |
| 持久化字段 | **34 个**（`schemaVersion` 由迁移消费，比对 33 个） |
| 启动瞬间**逐字读回** | **32 / 33** |
| 唯一差异 | `dailyBest: {} → {date:"",wins:0,…}` —— **空结构被 `validateSave` 规范化**，**无信息丢失** |
| **防篡改（对照）** | 改 `coins=999999` 而不动 `chk` → 读回 **0** ✅ 校验和拒了 |
| 空存档（对照） | 正确 FAIL |

⇒ **结论：存档往返干净**（第 23 轮判定完成；快照取在**启动瞬间**，故与「跑不跑实战」无关）。
⚠ 本判据修过一次**口径错**：第一版拿 A 的**内存快照**比 B 的读回值，报出 `totalKills: 239 → 405`——
实则落盘时内存已 405、存储里仍是 239，**两边本就该不同**；wrapper 键名我先按 `.data` **猜**，实测是 `.d`。

## 三·七、切后台与存档导出：又一个「垫片把信号写死」（第 42 轮）

> **同一个病根，第三次**：适配层是「用 `wx` 补出浏览器 API」的垫片。**凡是被垫片写成常量、或干脆缺失的信号，
> 母版里依赖它的分支都会静默失效** —— 不报错、不抛异常，只是那件事永远不发生。
> 第一次是安全区（`window.__wxadapter` 只挂 root 没挂 `win`，见三·五），本轮又抓到两处。

### 缺口 A：切后台**从不暂停**（母版那条路径一次都没跑过）

母版 `onVisibility()` 监听 `document.hidden` + `visibilitychange`，负责四件事：**立即暂停 → 弹暂停菜单 →
`Storage.save` 写档 → `Audio.suspend()` 挂起音频**（另加释放战斗指针），注释原文「hidden 立即暂停, 回来不自动恢复,
由玩家在暂停菜单点继续」。而适配层：① `document.hidden` 是 `get hidden() { return false }` **硬编码**；
② **完全没注册 `wx.onHide/onShow`** ⇒ 母版那段代码在小游戏里**一次都没执行过**：切走不暂停、回来没有暂停菜单、
不写档、音频不挂起。

**修**（`adapter.js`）：`wx.onHide/onShow` → 翻 `hidden` 标志 + 派发 `visibilitychange`。
⚠ 只派发 `visibilitychange`：母版同时监听 `pagehide` 是给 iOS Safari 用的，两条都派发会让同一个 handler 跑两遍。

**验证（阶段 ⑭）**：切后台 → 暂停 ✅ 写档 **4→5** ✅ 局内时钟冻结在 **0.6s** ✅；回前台 → **不自动恢复** ✅，
点「继续」后时钟恢复 ✅；并且**切走 60 秒回来不快进**（`dtCap=0.1` 生效：恢复后 10 帧只推进 <1s，若无钳制会是 ≈60s）。
阴性对照 `--no-hide-bridge`（桩里不给 `wx.onHide/onShow`）→ ❌ ⑭ + `exit 1`。

### 缺口 B：存档**导不出来**（编码层先断，剪贴板再断一次）

母版导出 = `exportSaveText()` = `JSON+chk` → `encodeURIComponent` → **`btoa`**。而小游戏**没有 `btoa/atob`**
（它不是浏览器），`escape/unescape` 也属 Annex B 遗留全局、运行时不一定给 ⇒ `Platform.Coding.encode()` 被
`try/catch` 吞掉后返回 `null`，**存档码根本生不出来**。就算生出来，复制这层也是死的：母版 `Clipboard.copy()`
两条路（① `navigator.clipboard.writeText` ② `textarea + execCommand`）在垫片里都不通 ⇒ 恒 `false`，
设置页显示「已生成存档代码(见下方, 可手动复制)」—— 可**画布上画出来的代码根本没法框选**，
那条降级路径在小游戏里等于不存在。

**修**：① 自己实现 `btoa/atob` + `escape/unescape`（浏览器语义：`btoa` 收 latin1 字节串、越界/非法字符**抛错**，
母版的 `try/catch` 会把它转成降级）；② `navigator.clipboard.writeText` → **`wx.setClipboardData`**。

**验证**：编码层**单元对拍 33/33**（与 Node 内置 base64/`escape` 逐项一致，覆盖空串 / 1–4 字节 / 中文+emoji /
含 `%` 的文本 / 母版真实的 `encode→decode` 顺序）；阶段 ⑮ 走**真实链路**：存档码 **1324 字符** base64 →
解码回 JSON 含 `d`/`chk` → 进剪贴板 ✅。阴性对照 `--no-clipboard-bridge` 与 `--no-b64` → ❌ ⑮ + `exit 1`。

> ⚠ **P1 教训（本轮自己踩的）**：⑮ 第一版只调 `Clipboard.copy(一个假字符串)`，**没测喂给它的编码层** ——
> 那是典型的「探针不对位」：编码断了它照样全绿。改成从 `exportSaveText()` 起测，才把 `btoa` 缺失抓出来。

### ⛔ 导入存档仍然不可用（**明确记录，不是遗漏**）

`Clipboard.paste()` 的契约是**同步返回字符串**（H5 用 `window.prompt`），而 `wx.getClipboardData` /
`wx.showModal({editable:true})` **全是异步** ⇒ 适配层无法在不改游戏语义的前提下实现它。
硬凑只有一条路：回前台预取剪贴板 + 点「导入」直接吃 —— 那会**绕过母版「导入会覆盖当前进度」的确认**，
属于改产品行为而不是补适配。要恢复导入必须**游戏侧加异步入口**（母版改动，另立版本）。

**产品含义**：小游戏形态下存档**只在本机**（0 网络请求是备案路线换来的），换设备不能迁移；
导出能把码存进微信聊天/备忘录，导入暂时只能靠 H5 形态。

**本机验不到的**：真机上 `wx.onHide` 的触发时机、音频 suspend/resume 的真实表现、rAF 是否真的停 ——
桩是模拟的，只能用开发者工具/真机复核（见 §五）。

## 三·八、资源分包：主包 **3.75 → 1.89 MB**（第 52 轮）

**为什么做**：分包前主包 = 代码 1.79 MB + `assets/` 1.99 MB = **3.76 / 4.00 MB（94%）**。
平台线是**悬崖** —— 再进一批美术就**传不上去**，而且失败发生在"上传"那一步，本地毫无预兆。

**官方口径**（2026-09 抓取，[分包加载](https://developers.weixin.qq.com/minigame/dev/guide/base-ability/subPackage/useSubPackage.html)）：

- 整个小游戏所有主包 + 分包 ≤ **30M**；主包 ≤ **4M**
- 单个普通分包 **不限制大小**；单个独立分包 ≤ 4M
- 「配置在 `subpackages` 字段内的目录或 js 文件，将按照配置打包成一个个「分包」，**没有配置在 subpackages 中的目录和 js，将会被打包到主包中**」⇒ 声明即分出
- ⚠ 旧资料里的「总包 20M（开通虚拟支付后 30M）」是**过时口径**，官方现文档写 30M，别按 20M 自缚

**怎么做的（三处，缺一不可）**：

| 处 | 改动 | 理由 |
|---|---|---|
| `game.json` | `subpackages: [{ "name": "assets", "root": "assets/" }]` | 声明即分出，**不需要任何构建步骤**；资源路径不变（仍是 `assets/x.webp`） |
| `game.js` | `wx.loadSubpackage({name:'assets'})` **成功之后**才 `require('./game.bundle.js')` | 分包里的文件在成功之前**不存在**，而母版对缺图是**静默回落程序化剪影**（不报错、不崩）⇒ 顺序写错的表现就是「上线后玩家看到一屏色块」 |
| `build-minigame.mjs` | 主包口径改为「目录实字节 − 已声明分包目录」＋ **余量 ≥1 MB 政策线** | 分包归属**读 `game.json` 决定**，不硬编码；政策线是平台线之外的自我约束 |

**实测（本机可复跑）**：

```
主包   1.89 MB / 4.00 MB（余量 2.11 MB）   ← 分包前 3.76 MB（余量 0.24 MB）
分包   assets/  178 个文件 / 1.99 MB       ← 单个普通分包不限大小
总包   3.88 MB / 30.00 MB（余量 26.12 MB）
```

`1.89` 是**保守口径**（目录里所有文件都算进主包）；`project.config.json` 的 `packOptions.ignore`
还会剔掉 `smoke.mjs` / `build-minigame.mjs` / `README.md` / `_L.log` 共约 0.11 MB
⇒ 实际上传主包 ≈ **1.79 MB**。

**入口的 4 个分支（全部进冒烟，阶段 ⑯b）**：

| 场景 | 怎么跑 | 期望 |
|---|---|---|
| 成功（默认） | `node smoke.mjs` | 先 `loading` 且**不启动**；success 之后才启动，`state=ok` |
| 下载失败 | `node smoke.mjs --subpackage-fail` | `state=fail` 且**兜底启动**（可玩 > 白屏），并留 `__retryAssetsSubpackage` |
| 老基础库没有该 API | `node smoke.mjs --no-loadsubpackage` | `state=skipped`，直接启动（官方：< 2.1.0 由后台下发整包兼容代码） |
| **永不回调** | `node smoke.mjs --subpackage-stall` | **必须不启动** —— 这条是阴性对照，证明门控真的在等、不是摆设 |

**判据自测**：`node build-minigame.mjs --selftest` ⇒ **6/6** 例符合预期
（① 内联母版 ② 未分包 ③ 已分包 ④ 声明了空目录 ⑤ 主包超 4M ⑥ 总包超 30M）；
阶段 ⑯a 另有 3 条构造错误（声明缺失 / root 写错 / 入口不调 `loadSubpackage`）必须全被抓到。

**⛔ 本机验不到**：开发者工具/真机里的**实际上传**（分包有没有被正确打进代码包、`loadSubpackage` 的真实下载耗时与失败率）。
本机能证明的是「配置正确、入口顺序正确、体积口径保守」三件事，**不是**「上传成功」。

## 四、音频：两条路，二选一（**这是移植唯一需要你拍板的取舍**）

母版 `tryLoadLocalFiles()` 第一行就是 `if (typeof fetch === "undefined") return;`，
注释原文「缺槽保持程序化。零网络」「禁止 http(s) CDN」。所以：

| 路线 | 做法 | 包体 | 音质 |
|---|---|---|---|
| **A（推荐首版）** | 适配层**不提供 `fetch`** | **3.74 MB 单主包** | 程序化合成音频（设计内一等路径：`DATA_BGM` 表自带 beats/bpm，门禁 `bgm-spec-coherence` 正是守它） |
| B（增强） | 适配层把 `fetch` 映射到包内文件读取 + 29 个 WAV 进分包 | 3.74 + **7.00 MB** ≈ 10.7 MB（仍 ≤30MB） | 用仓库里那 29 个 WAV 渲染件 |

> 路线 B 的 WAV 共 **7.00 MB**（最大 `bgm_march.wav` 1.44 MB）。若要上 B，建议先转码成 MP3/AAC：
> 通常能压到 1/8 左右，可把它塞进主包。

**✅ 路线 A 已实测验证有声音（第 18 轮）**：`smoke.mjs` 的 ⑩ 阶段会断言音频路径真的活着。
实测台账（3000 帧对局）：

```
AudioContext×1   bufferSrc×557   gain×559   buffer×30   start×530   connect×1062
```

**30 个 AudioBuffer ≈ 10 BGM + 19 SFX** 的程序化合成数，**530 次 `start()`** ⇒ 确实在发声。

> ⚠ **这一条差点漏掉**：适配层最初**一处音频映射都没有**，而母版 L12865 是
> `var AC = window.AudioContext || window.webkitAudioContext;` 且**静默降级**
> （拿不到就 `ctx=null`，`play` 内再守卫 → **整局无声且不报任何错**，源码注释原文
> 「无 AudioContext 环境亦置位(play 内再守卫, 静默无声)」）。
> ⇒ **"游戏能跑通"绝不等于"有声音"**；⑩ 就是为这一类"静默降级"设的专项断言，
> 阴性对照 `--no-audio`（抽掉宿主 WebAudio 工厂）会正确地报 FAIL。

## 五、还没验的（**本机做不到，必须真机/开发者工具**）

诚实列清楚，避免把"本机绿"当成"真机没问题"：

- 微信开发者工具里的**真机预览**与**上传**（需要你的 AppID 与登录）。
- 分包的两件事：**上传时 `assets/` 有没有被正确打进分包**、`loadSubpackage` 在真机的**下载耗时与失败率**
  （本机只能证明"配置对、入口顺序对、体积口径保守"，见 §三·八末尾）。
- iOS / Android 真机上的**触摸手感、帧率、内存**。
- 真实 `wx.createImage()` 对 `assets/*.webp` 的**解码支持**（WebP 在 iOS 小游戏上的支持需实测）。
- 音频路线 B 的 `decodeAudioData` 对 WAV 的实际支持。
- ⚠ **结构性缺口：本工程在仓库外 ⇒ 云端那 104 条门禁一条也没覆盖它**，这里的 `build-minigame.mjs` 与
  `smoke.mjs` **只有我手动跑的时候才会跑**。要让它进 CI，得把工程移进仓库
  （**源文件仅约 135 KB**：`game.js`/`game.json`/`adapter.js`/`build-minigame.mjs`/`smoke.mjs`/配置/本 README；
  `game.bundle.js` 与 `assets/` 是构建产物，进 `.gitignore` 后由 CI 现场 `node build-minigame.mjs` 生成 —— 仓库里
  `dist/assets` 的 **178 个文件全部已被 git 跟踪**，所以云端重建是可行的、已核过）。
- ⚠ **已知风险（本机量出来的，第 19 轮已修正）**：启动期创建 **1105 张画布、合计 49.0 Mpx ≈ 187 MB**（@RGBA）。
  ⚠ **前一版数字（407 张 / 116 MB）是被错误桩低估的**：那时图片桩永远返回 **128×128 假图**，
  而真实素材是 **384×384 ×135 张**等 18 种尺寸 —— 预渲染画布按真实尺寸分配，所以真值高出约 40%。
  用真图桩（读真实文件、解真实尺寸）复测得：**1105 张 / 49.0 Mpx ≈ 187 MB**。
  这仍是**一次性预渲染缓存、不是每帧泄漏**（帧数 900→12000 时只从 410 涨到 414）。
  PC 无感，但**低端手机上 187 MB 画布是真实的 OOM/掉帧风险**，建议真机上先只看内存曲线。

## 五·二、广告：**首版不发广告**（保留桩）

母版的广告路径是**一个桩对象**，不是真 SDK：

```js
// AdService stub: HTML 阶段直接同步回调 onReward, UI 不出现"看广告"字样。
var AdService = { showRewarded: function (onReward, onFail) { onReward(); } }
```

复活 / 结算翻倍 / 挑战再开**只走这一个对象**。**首版移植保持原样 = 完全不发广告**，
审核面最小（也避开"虚假广告按钮"这类真会被卡的问题）。
将来要接激励视频，只需替换 `AdService.showRewarded` 一处为
`wx.createRewardedVideoAd` + `onClose` 判 `res.isEnded === true`（母版注释已写明）。

## 五·三、WebP 万一在真机不可解码：退路已量好

若 `wx.createImage()` 在某平台不能解 `.webp`，退路是**换成 PNG 并把美术放进分包**：

| 方案 | 美术体积 | 主包 | 结论 |
|---|---|---|---|
| 现状（178 张 webp） | 1.98 MB | **3.74 MB** ✅ | 单主包 |
| 换 PNG（调色板压缩，实测 178 张） | **4.79 MB**（2.41×） | 1.74 + 4.79 = **6.54 MB** ❌ | **必须把美术挪进分包**（普通分包不限大小） |

⇒ 换格式**不能**塞回主包；真要退，退法是"美术进分包"，不是"改格式"。
